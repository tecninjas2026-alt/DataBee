| Parte | Regra proposta |
|---|---|
| `id` | UUID único, default automático; o cliente gera o id antes para compor o caminho |
| `observation_id` | Obrigatório e único: só uma foto por observação |
| `owner_id` | Padrão = conta atual; chave estrangeira composta garante o mesmo dono da observação |
| `object_path` | Obrigatório e único; formato `owner_id/observation_id/id.jpg` para JPEG ou `.png` para PNG |
| `mime_type` | Somente `image/jpeg` ou `image/png` |
| `bytes` | Inteiro maior que zero e no máximo 5.242.880 bytes, igual ao limite de 5×1024×1024 do app |
| `position` | Inteiro não negativo, padrão 0; não permite segunda foto porque observation_id é único |
| `created_at` | Gerado pelo banco; cliente não informa |
| `photo_source` | `camera` ou `gallery`; na inserção do cliente, precisa coincidir com a origem da observação |
| SELECT | Dono lê os próprios metadados; B e anônimo não leem os de A |
| INSERT | Somente dono em observação própria, lifecycle draft e analysis_status idle |
| UPDATE/DELETE | Sem grants ou políticas para cliente; mudanças e limpeza ficam com backend autorizado |

RLS confere **linhas** (o porteiro do banco); grants limitam **operações e colunas**. A chave composta `(observation_id,owner_id)` protege a coerência do dono também fora da política. A origem não é deduzida do MIME: uma foto da galeria convertida em JPEG continua `gallery`.

O caminho é uma convenção técnica reproduzível já compatível com o formato solicitado para a IMP-015. Não aceita URL pública, URL assinada, query string ou nomes pessoais. Não armazena foto/binário. O id é gerado antes do upload, para que o mesmo identificador seja usado no nome do arquivo e nos metadados. A IMP-014 não verifica a existência ou o conteúdo de arquivo: bytes e MIME aqui são dados declarados; upload e validação real pertencem às próximas tasks.

Não há bucket ou política de `storage.objects` nesta migration, nem tela/fluxo de salvamento. A remoção administrativa futura de uma observação pode remover seus metadados em cascata; não apaga objetos do Storage, cuja limpeza será tarefa do backend. Nenhuma exclusão real faz parte desta proposta.

## 🎓 Explicação para a equipe

Uma observação é a ficha do encontro com a abelha. `observation_images` é a etiqueta da foto dessa ficha: diz onde o arquivo fica, seu formato, tamanho e se veio da câmera ou da galeria.

**Entrada → processamento → saída:** dados da foto → banco confere dono, estado e limites → grava uma etiqueta ligada à observação. A foto em si irá para a pasta privada da IMP-015. A etiqueta armazena o caminho, nunca o arquivo inteiro.

**Como revisar agora:** abrir a migration e conferir uma foto por ficha, mesmo dono, limites de tamanho/formato e bloqueio de alteração direta. Ainda não há mudança visível no app. Depois da autorização, o agente aplica e prepara a página para a equipe executar o teste real A/B com metadados sintéticos.

<details><summary>Por que o banco não guarda a foto inteira?</summary>O arquivo fica no Storage. A tabela guarda uma etiqueta pequena com o caminho e as informações necessárias para relacioná-lo à observação.</details>

<details><summary>Converter para JPEG muda a origem para câmera?</summary>Não. Formato é o tipo do arquivo; origem é como a foto entrou no app. Uma foto da galeria continua gallery após a conversão.</details>

<details><summary>Posso trocar os metadados depois de criar?</summary>O cliente não recebe UPDATE/DELETE. Limpeza e mudanças posteriores precisam de backend autorizado, para manter a relação com o arquivo.</details>
