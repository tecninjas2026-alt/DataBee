### SQL proposto e arquivos

- [Migration completa](../../supabase/migrations/20261016032127_imp013_observations_private_locations.sql).
- [Tipos de leitura e escrita do cliente](../../src/app/core/models/observation.model.ts).
- Este registro e `docs/HANDOFF.md`.

O SQL cria somente duas tabelas e seus índices, restrições, permissões e políticas. Não cria telas, Storage, funções, IA ou dados iniciais.

| Parte do SQL | Efeito proposto |
|---|---|
| `observations` | UUID automático; vínculo ao usuário de Auth; `created_at = now()`; captura opcional, sem data presumida; estados iniciais `draft/private/idle`, curadoria NULL |
| `photo_source` | Mantém a origem camera/gallery já prevista no modelo do app e em D21 |
| Região ampla | NULL ou um dos dois rótulos de D10; escrita reservada ao backend |
| `observation_private_locations` | Uma localização opcional por observação; latitude/longitude obrigatórias apenas quando a linha existe; accuracy opcional, não negativa e finita |
| Origem e consentimento | Três origens aceitas; `device_gps` exige `consent_at`; outras origens admitem NULL |
| Vínculo composto `(observation_id, owner_id)` | O dono da localização precisa ser o mesmo da observação, mesmo quando a operação vem de um serviço privilegiado |
| `enable row level security` | Liga RLS nas duas tabelas. RLS é o porteiro: filtra quais linhas cada conta pode acessar |
| `revoke` seguido de `grant` por coluna | Retira permissões amplas e devolve somente as necessárias; impedir edição na tela não bastaria |
| Políticas de INSERT | Somente observação própria, inicialmente privada e sem análise/curadoria; localização somente em observação própria |
| Políticas de SELECT/UPDATE | Dono lê e altera somente as linhas próprias; UPDATE da observação limitado a `captured_at`; na localização, somente seus dados e consentimento |
| Estados protegidos | Cliente não recebe INSERT/UPDATE para estados, `analysis_started_at`, `public_region_label` nem `created_at` |
| Identificadores protegidos no UPDATE | Cliente não transfere `user_id`, `owner_id` ou `observation_id` |
| Anônimo e DELETE | Sem grants de acesso para anon; sem DELETE para cliente autenticado |
| `service_role` | Permissões para backend confiável; essa credencial nunca vai ao app. Esta task não implementa rotinas de validação humana |
| Exclusão em cascata | Remoção administrativa do usuário/observação remove filhos vinculados; não concede exclusão ao cliente |

`captured_at` confiável e consentimento real dependem do fluxo humano: o banco confere o formato e as restrições, não consegue provar sozinho quando a foto foi tirada ou se alguém consentiu. Não existe linha de localização sem coordenadas nem coordenada inventada para representar recusa.

Uma consulta simples `select('*')` de observations retorna apenas suas colunas, que não contêm GPS. A localização separada continua sujeita às próprias políticas, inclusive em consultas com relacionamento. A migration não libera leitura pública de observações publicadas; o feed pertence a outra task.

## 🎓 Explicação para a equipe

Entrada: a pessoa registra uma foto e decide se informa localização → processamento: o banco confere dono, campos permitidos e limites → saída: um rascunho privado e, se houver consentimento/dados, uma linha separada de localização. Essa é a estrutura proposta; o botão Salvar será ligado em outra tarefa.

Pense em duas gavetas: uma guarda a ficha da observação; outra guarda a localização exata. O porteiro RLS só abre as gavetas do dono. As permissões de coluna são como espaços de um formulário que somente a equipe autorizada pode preencher: uma pessoa comum não pode escrever “validado por cientista”.

Pode falhar por sessão vencida, falta de permissão, dado inválido ou queda de conexão. A recusa de GPS não é erro: basta não criar a segunda linha. Sem fonte confiável, a data original da foto fica vazia; a data de criação continua registrada automaticamente.
