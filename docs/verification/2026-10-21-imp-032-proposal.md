Somente o apelido de cadastro é copiado. Não é derivado do e-mail. Metadados de usuário não definem autorização nem papéis. O SQL remove espaços comuns das pontas do apelido de cadastro e rejeita valor ausente, que não seja texto, vazio, só com espaços em branco ou maior que 80; nesses casos usa Participante. Na inclusão de contas antigas, `created_at` significa criação do perfil agora, sem inventar data histórica.

O uso de trigger e a separação de permissões seguem as referências oficiais consultadas: [perfis vinculados a Auth](https://supabase.com/docs/guides/auth/managing-user-data), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) e [permissões por coluna](https://supabase.com/docs/guides/database/postgres/column-level-security). Um erro no trigger pode impedir cadastro: cadastro real e metadados inválidos precisam ser verificados após autorização no projeto de desenvolvimento.

### Roteiro após aplicação e integração

Todos os casos abaixo estão **Não executados**. Usar o cliente Supabase com chave pública e contas reais; SQL administrativo não prova permissões. Credenciais entram somente na ferramenta local privada do responsável, nunca no chat ou relatório. Resultados e evidências devem usar rótulos A/B, sem nomes reais.

| Caso | Esperado |
|---|---|
| A entra duas vezes | Mesmo perfil, mesmo `created_at`, sem duplicação ou sobrescrita de apelido |
| A reabre com sessão válida | Perfil carregado do banco |
| A sai e B entra; resposta de A chega atrasada | Nenhum apelido de A aparece como sendo de B |
| A lê perfil de B | Permitido; somente `id`, `display_name`, `created_at` |
| B tenta alterar apelido de A | Zero linhas alteradas; releitura confirma apelido intacto |
| A tenta inserir perfil de B | Recusado por RLS, mesmo sem conflito de chave |
| Anônimo tenta ler/inserir/alterar perfil | Acesso recusado |
| A altera o próprio apelido para valor válido | Permitido via cliente; leitura persiste o novo valor |
| A tenta alterar `id` ou `created_at`, ou enviar data no INSERT | Recusado por permissão de coluna |
| A envia nome vazio, só espaços em branco ou 81 caracteres | Recusado pelo banco; nomes de 1 e 80 aceitos |
| Cliente tenta DELETE | Recusado; não executar exclusão administrativa como teste |
| Cadastro de conta de teste com apelido válido | Um perfil criado automaticamente |
| Cadastro autorizado de teste sem nome, com nome inválido ou não textual | Perfil com Participante; cadastro não falha por esse metadado |
| Duas criações concorrentes do próprio perfil ausente | Uma linha, sem trocar apelido salvo |
| Falha de rede ao carregar perfil | Erro tratado; sem perfil falso ou de outra conta |

Não apagar perfis existentes para simular ausência. O caso de recuperação exige fixture/conta de teste preparada e autorizada; executar INSERT com id de B já existente não prova sozinho o bloqueio de propriedade, porque pode falhar apenas por chave duplicada.

## 🎓 Explicação para a equipe

O perfil é uma ficha pequena ligada à conta: número da ficha, apelido e data de criação. O e-mail continua na autenticação, que é o controle de entrada.

**Entrada → processamento → saída:** cadastro com apelido → banco confere e cria a ficha → perfil salvo em `public.profiles`. Quando o app for integrado, entrar novamente buscará a mesma ficha. Participante é o nome provisório para cadastro sem apelido válido.

**RLS é o porteiro do banco:** permite que participantes com login leiam os perfis, mas só o dono altere seu apelido. As permissões por coluna também protegem o número da ficha e a data.

**Migration é a receita da mudança:** o arquivo foi preparado no computador. A simulação mostrou qual receita será aplicada; o banco ainda não recebeu essa mudança. Nesta etapa não aparece funcionalidade nova no app.

**Como revisar agora:** abrir os arquivos acima e conferir os três campos, leitura entre pessoas com login, alteração somente pelo dono e Participante como fallback. Os testes com cliques no login vêm depois da aplicação e integração, com roteiro e resultados próprios.
